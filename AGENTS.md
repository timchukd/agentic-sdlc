# AGENTS.md

Instructions for AI coding agents working in this repository. Read this file fully before making changes. The glossary in `GLOSSARY.md` defines the domain language; use its terms exactly.

## 1. Project Description

**Customer Portal** is a backend service that lets people register, authenticate, and manage their profile. It is designed to grow into a product catalog, ordering, and customer support.

Current scope (v1):
- Registration with email verification
- Login, logout, token refresh with rotation and reuse detection
- Password reset
- Profile view and edit
- Account deletion (deactivate immediately, purge personal data after 30 days)

Out of scope for v1: catalog, ordering, support, staff roles, address book, marketing consent.

Domain terms: `User` (identity), `Profile` (personal data, 1:1 with User), `Customer` (role used by ordering and support contexts only), `Role` (v1: `customer` only), `Session` (identified by a refresh token).

| Area | Choice |

Library documentation: before implementing with any library or framework, or adding a feature that uses one, check current docs with Context7 (`resolve-library-id`, then `query-docs`). Do not rely on memory for FastAPI, SQLAlchemy, Pydantic, or Alembic APIs.

## 3. Architectural Constraints

**Modular monolith.** One deployable application split into bounded-context modules under `src/`:

```
src/
  identity/      # User, credentials, sessions, tokens, verification, password reset
  profile/       # Profile
  catalog/       # future
  ordering/      # future
  support/       # future
  platform/      # shared infrastructure: config, db session, logging, email port, outbox, errors
```

Rules:
1. Each module has layers: `router` (HTTP) → `service` (use cases) → `repository` (persistence). Routers never touch ORM models or the database session directly.
2. A module exposes its public surface through a `public.py` (or `__init__.py` exports). Other modules import only from that surface.
3. A module never reads or writes another module's tables or ORM models. Cross-module data access goes through the other module's service interface.
4. `platform/` contains no business logic and never imports from business modules.
5. Dependencies are injected through FastAPI `Depends` and interfaces (ports), so services are testable without HTTP or a real email provider.

**Transactions and events.**
- A use case that changes state and must send email writes the email to the `outbox` table in the same transaction as the state change.
- A background worker reads the outbox and sends messages. It retries on failure and is idempotent.
- Do not send email inline from a request handler and do not use FastAPI `BackgroundTasks` for email.

**API design.**
- REST under `/api/v1/...`. Breaking changes require a new version prefix.
- Errors follow RFC 9457 (Problem Details), with a stable machine-readable `code` field. The backend never returns translated, user-facing text.
- Every request and response body is a Pydantic model. No raw `dict` in public signatures.
- The OpenAPI schema generated by FastAPI is the frontend contract. Keep it accurate: explicit response models, documented error codes.

**Security requirements.**
- Passwords: minimum 12 characters, maximum 128, no composition rules. Reject passwords found in Have I Been Pwned using the k-anonymity range API (send only the SHA-1 prefix).
- Passwords and tokens are never logged, returned in responses (except the one-time values intended for the client), or stored in plain text. Refresh tokens are stored as hashes.
- Rate limits on `login`, `register`, and `forgot-password`, applied per IP and per email. After 10 failed logins on an account, block it for 15 minutes. No permanent lockout.
- Access tokens: 15 minutes. Refresh tokens: 30 days sliding, 90 days absolute maximum from login. Every refresh rotates the token. Reuse of a rotated refresh token revokes the whole session.
- `register` and `forgot-password` return identical responses whether or not the email exists. If the email is already registered, send a notice email instead of an error.
- Email is stored normalized to lowercase and is unique. Changing email requires verifying the new address; the old address stops working once the new one is verified.
- Account deletion: deactivate immediately (block login, revoke sessions). Hard-delete personal data after 30 days. Retained history references an anonymized User with no PII.

**Data model rules.**
- Primary keys are UUIDv7 (generated in the application).
- Every table has `created_at` and `updated_at` (timezone-aware, UTC).
- Timestamps are stored as `timestamptz`. No naive datetimes anywhere.
- Schema changes are made only through Alembic migrations. Never edit the database by hand. Every migration must be reviewed for reversibility and for lock duration on large tables.

**Profile fields (v1):** `first_name` and `last_name` (required), `phone` (optional, E.164), `preferred_locale` (default `en`), `time_zone` (IANA name, default `UTC`).

## 4. Conventions

**Code style**
- Everything is `async` where I/O is involved. Do not call blocking I/O from async code.
- Full type annotations. `mypy --strict` must pass. No `Any` without a justifying comment.
- Prefer `pydantic` models for structured data, `dataclasses` or `attrs` only for pure domain value objects without validation needs.
- Use `Annotated[...]` with `Depends` for dependency injection aliases.
- Use `Enum` (`StrEnum`) for fixed value sets.
- Write small functions with explicit names. Avoid hidden side effects at import time.
- No global mutable state. Configuration comes from `pydantic-settings` only.

**Naming**
- Code, identifiers, comments, commit messages, and documentation: English.
- Modules and packages: lowercase, singular nouns (`identity`, `profile`).
- Service methods are use-case verbs: `register_user`, `verify_email`, `refresh_session`.
- Routes are nouns with HTTP methods: `POST /api/v1/sessions`, `GET /api/v1/profile`.

**Configuration and secrets**
- All configuration is read from environment variables via `pydantic-settings`. Secrets have no defaults.
- Local development uses a `.env` file, which is git-ignored. Commit `.env.example` with placeholder values.

**Logging**
- Structured JSON logs through structlog. Include `request_id`, `user_id` (if known), and event name.
- Log at `INFO` for business events, `WARNING` for recoverable anomalies (e.g., reuse of a refresh token), `ERROR` for failures.
- Never log passwords, tokens, or full email addresses (mask them).

**Database**
- Repositories return domain-level objects or simple DTOs, not ORM instances, to callers outside the module.
- No N+1 queries: use explicit `selectinload` or `joinedload`.
- Use transactions explicitly at the service layer. Repositories do not commit.

**Git**
- Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`).
- Small, focused commits. Each commit leaves the test suite green.
- Feature branches merged to `main` through pull requests.

**Documentation**
- `GLOSSARY.md` holds domain terms only. It contains no implementation details.
- Architecture decisions that are hard to reverse, surprising, and the result of a real trade-off are recorded as ADRs in `docs/adr/`.

## 5. Testing Requirements

**Layers**
- **Unit tests** (`tests/unit/`): services and domain logic with fake repositories and fake ports. No database, no network. Fast.
- **Integration tests** (`tests/integration/`): repositories and migrations against a real PostgreSQL 17 started by testcontainers. Never use SQLite, and never mock the database in integration tests.
- **API tests** (`tests/api/`): HTTP behavior through `httpx.AsyncClient` with the ASGI transport. Assert status codes, RFC 9457 bodies, and error `code` values.
- **Migration tests**: every migration applies cleanly on an empty database and on a database seeded with the previous revision.

**Coverage**
- Overall line and branch coverage: at least 85%.
- `identity` and `profile` modules: at least 95%.
- Coverage is a floor, not a goal. Tests must assert behavior, not just execute lines.

**Rules**
- Every bug fix starts with a failing test that reproduces the bug.
- Every new endpoint has API tests for success, validation failure, authentication failure, and authorization failure.
- Security-relevant behavior (rate limiting, lockout, token rotation, reuse detection, anti-enumeration) has dedicated tests.
- Tests are deterministic: inject clocks and random sources; no `sleep` for timing.
- Test data is created through factories or fixtures, not shared mutable state.
- Each test is independent and runs in any order (`pytest-randomly` or equivalent in CI).
- External services (email, HIBP) are faked in tests. The HIBP adapter has contract tests with recorded responses.

**Tooling commands** (must work from a clean checkout):
- `uv sync` installs dependencies.
- `uv run ruff check . && uv run ruff format --check .`
- `uv run mypy src tests`
- `uv run pytest` runs the full suite including coverage.

## 6. Definition of Done

A change is done only when all of the following are true:

1. The behavior is specified: the relevant glossary terms are used, and the acceptance criteria are stated in the pull request.
2. Tests are written first or alongside the code, and they cover success and failure paths. The new code is covered per Section 5.
3. `ruff check`, `ruff format --check`, `mypy --strict`, and `pytest` all pass locally and in CI.
4. Database changes have an Alembic migration that applies and downgrades cleanly, and the migration tests pass.
5. Public API changes update the OpenAPI schema, the error codes, and the API documentation. Breaking changes use a new version prefix.
6. No secrets, tokens, or personal data appear in code, logs, fixtures, or test snapshots.
7. Security-relevant changes are reviewed against Section 3 (security requirements).
8. Module boundaries are respected: no cross-module table access, no business logic in `platform/`.
9. Configuration additions are documented in `.env.example`.
10. The change works in the Docker Compose environment (`docker compose up` starts the app and the migrations run).
11. Commits follow Conventional Commits, and the pull request is small enough to review in one sitting.

## 7. Prohibited Actions

Agents must not do any of the following without explicit approval from the repository owner:

- Commit secrets, credentials, `.env` files, private keys, or real personal data (including in test fixtures or seed data).
- Disable, skip, or weaken tests, linters, or type checks (`# type: ignore`, `# noqa`, `skip`, `xfail`) to make a change pass. If a suppression is truly needed, it must have a comment explaining why.
- Use SQLite, or mock the database, in integration tests.
- Modify an existing Alembic migration that has been merged to `main`. Create a new migration instead.
- Edit the database schema by hand or with `create_all` outside of migrations.
- Log or return passwords, password hashes, access tokens, refresh tokens, or full email addresses in error responses.
- Store passwords with any algorithm other than Argon2id, or store refresh tokens in plain text.
- Add a dependency that is unmaintained, has no clear license, or duplicates an existing one, without noting it in the pull request.
- Introduce cross-module imports of internal modules or access another module's tables.
- Put business logic in routers or in `platform/`.
- Send email synchronously from request handlers or use `BackgroundTasks` for email.
- Change public API responses or error codes in a breaking way within `/api/v1`.
- Return user-facing translated text from the backend.
- Reveal whether an email is registered in any response of `register` or `forgot-password`.
- Introduce new authentication flows, or relax rate limits and lockout rules, without an ADR and owner approval.
- Use `Any` or untyped functions in new code.
- Push directly to `main`, force-push to shared branches, or bypass CI.
- Use blocking I/O (`requests`, synchronous DB drivers, `time.sleep`) inside async code paths.
- Upgrade the Python version, PostgreSQL major version, or change the framework without an ADR.

## 8. Working Agreement for Agents

- Read `GLOSSARY.md` and this file before starting. If a requirement conflicts with this file, stop and ask rather than deciding silently.
- Make the smallest change that satisfies the request. Do not refactor unrelated code in the same change.
- When a decision is hard to reverse and was made for a real reason, propose an ADR in `docs/adr/`.
- If you find a contradiction between code and `GLOSSARY.md`, surface it and ask which one is correct.
